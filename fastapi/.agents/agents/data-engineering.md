# Data Engineering Standards

Стандарт для дата-инженерных компонентов: ETL-приложения, Airflow DAG'и, Kafka-воркеры, загрузка данных в ClickHouse, выгрузка из ClickHouse в S3. Дополняет общие стандарты (`python-standards.md`, `error-handling.md`, `logging.md`, `testing.md`, `database.md`), а не заменяет их. Где данные-инженерный код расходится с веб-сервисным (FastAPI/async) — расхождения описаны явно ниже.

Эталон стиля — уже работающее ingest-приложение вашего ETL-монорепозитория: пара «CLI-приложение (`docker_apps/<app>/`) + его DAG (`dags/<app>/`)». Новые компоненты копируют её паттерны.

***

## §0. Когда применять этот стандарт

- Пакетные (batch) CLI-приложения, запускаемые Airflow через `KubernetesPodOperator`.
- Airflow DAG'и.
- Kafka-воркеры (consumer/producer).
- Загрузка данных в ClickHouse и выгрузка из него (в т.ч. в S3/OBS).
- Любой код, который двигает данные между источниками (S3, Kafka, CH, Postgres), а не обслуживает HTTP-запросы.

Для HTTP-сервисов (FastAPI) — общий `python-standards.md`.

***

## §1. Отличия батч-кода от веб-сервисного (важно)

`python-standards.md` написан под async FastAPI-сервис. Дата-инженерный batch-код осознанно отступает от него по трём пунктам:

| Аспект | Веб-сервис (python-standards) | Дата-инженерный batch |
|---|---|---|
| I/O | async (`httpx.AsyncClient`, `AsyncSession`) | **синхронный** (`clickhouse_connect`, `boto3`, `psycopg`) — под живёт ради одной задачи, event loop не нужен |
| Параллелизм | `asyncio.TaskGroup` | `multiprocessing` (см. `runtime.resolve_workers`) для CPU/IO-bound файловой обработки |
| Логирование | `structlog` | stdlib `logging` (`logging.basicConfig` один раз на старте) |
| Конфиг | `pydantic-settings` | `pydantic-settings` (то же) |

**Универсальные правила соблюдаются всегда** (из `python-standards.md`): аннотации типов везде, `from __future__ import annotations`, нет `except Exception: pass`, нет mutable default, magic numbers в константы, DTO/dataclass а не `dict` на границах, fail-fast на битой конфигурации, параметризованный SQL, нет секретов в логах, docstring Google-style на русском (см. `AGENTS.md`).

### §1.1 Соотношение с существующими стандартами (что НЕ применяется к batch)

Часть правил `python-standards.md` / `database.md` / `testing.md` написана под async FastAPI-сервис с Postgres. Они **не противоречат** этому стандарту — они просто относятся к другому типу компонента и к batch-коду не применяются. Чтобы не было разночтений:

| Правило в существующих стандартах | Где | Применяется к batch data-eng? |
|---|---|---|
| Async-правило: всё `async def`, `AsyncSession`, нет sync `requests`/`psycopg` | python-standards §5 | **Нет.** Относится к веб-сервису с event loop. Batch-под живёт ради одной задачи — синхронные `clickhouse_connect`/`boto3`/`psycopg` корректны. |
| `structlog` для сервиса | python-standards §13, logging.md | **Частично.** Для долгоживущего сервиса с request-контекстом — `structlog`. Для batch-CLI — stdlib `logging` (как в эталонном ingest-приложении). Правила «kwargs не f-строки», «не логировать секреты» — соблюдаем в обоих. |
| SQLAlchemy 2.0 async + Alembic, repository pattern, AsyncSession | database.md, python-standards §11 | **Нет для ClickHouse/Kafka/S3.** database.md управляет Postgres-БД сервиса. CH-доступ — `clickhouse_connect`, DDL — отдельными скриптами/миграциями, не Alembic. Если batch-app трогает Postgres сервиса — там действует database.md. |
| Тесты `async def` + `httpx.AsyncClient` + `ASGITransport` | testing.md | **Нет.** Batch-тесты синхронные (нет async-хендлеров). Остальное из testing.md (pytest, Fake вместо mock, без `unittest.TestCase`) — соблюдаем. |
| Тулчейн `uv run ruff` + `basedpyright` + pre-commit с ruff | python-standards §5, feature.md | **По факту репо.** В легаси ETL-репозиториях pre-commit обычно собран на `black`/`isort`/`flake8`/`mypy`/`bandit`/`pycln` (не ruff/basedpyright/uv). Следуем тулчейну целевого репо, см. §11. |

Если возникает реальный конфликт правил (а не разделение по типу компонента) — действуем по `error-handling.md` (Identify → Assess → Communicate), не молчим.

## §2. Структура приложения (CLI)

Канон — эталонное ingest-приложение. Один образ, режим выбирается аргументом CLI.

```
docker_apps/<app_name>/
├── __main__.py            # точка входа: from <app>.cli import main; main()
├── cli.py                 # argparse, --ingest/--export/--source, dispatch
├── app.py                 # run_<mode>(name): диспетчер по режимам
├── settings.py            # pydantic-settings, вложенные модели
├── const.py               # именованные константы (magic numbers сюда)
├── runtime.py             # resolve_workers и пр. runtime-утилиты
├── clients/               # clickhouse.py, s3.py, postgres.py — тонкие фабрики
├── ingest|export/         # бизнес-логика режимов
├── storage/               # checkpoint/watermark, batch insert, txt sink
├── dto.py                 # frozen dataclass'ы для границ
├── Dockerfile
├── requirements.txt
├── version.txt            # semver, стартует с 0.0.1
└── README.md              # что делает, список ENV, как запускать
```

Слои: `cli → app → ingest/export → clients/storage`. Бизнес-логика не в `cli.py`. Клиенты (`clients/*.py`) — тонкие фабрики (создать клиент по настройкам), без логики.

## §3. Настройки (pydantic-settings)

Канон — `settings.py` эталонного приложения. **Всё параметризуется, ничего не хардкодим.**

Правила:

1. `pydantic-settings` `BaseSettings`, `env_nested_delimiter="__"`, `case_sensitive=False`, `extra="ignore"`, `env_file=".env"`.
2. Вложенные модели на каждый источник/подсистему: `settings.clickhouse.host` читается из `CLICKHOUSE__HOST`.
3. **Пустая строка из ENV/GUI = «не задано».** Коэрсить через `BeforeValidator` (паттерн `empty_str_to_none` / `OptionalEnvInt` в эталоне). Не использовать пустую строку как смысловой сентинел — для «всё/по умолчанию» вводить явный токен (например `__all__`).
4. Секреты (пароли, ключи, токены) — только из ENV (на серверах — из k8s Secret), дефолт `""`/`None`, в коде/конфиге/гите не лежат (`security.md`).
5. **Fail fast:** при отсутствии обязательного (хост CH, креды S3) падать на старте с понятным сообщением, не работать «как-нибудь».
6. Целевые имена таблиц/топиков/бакетов — **в настройки**, не в код: они переименовываются, ренейм не должен требовать пересборки образа.
7. Лимиты (batch size, file size, workers, timeouts) — именованные поля настроек или константы `const.py`, не magic numbers.

## §4. Airflow DAG'и

Канон — DAG эталонного приложения. Правила (свод: эталон монорепозитория + принятые в команде «Правила работы с DAG»):

### §4.1 Именование и структура

- **Имя файла DAG = ID дага** (или максимально близко — для генерируемых дагов). Облегчает поиск.
- В имя дага **не пишем слово «DAG»** — и так понятно по расположению.
- Один DAG — задача на каждый источник/сущность (`KubernetesPodOperator` с разным `--source`/`--ingest`). Зависимости — через `chain()`.

### §4.2 Конфигурация дага через Pydantic (обязательно)

- **Параметры подключения** (хост/мета коннекта) каждого дага — в **отдельных переменных** (Airflow Variable или k8s Secret в зависимости от установки), чтобы смена хоста меняла их у всех дагов разом.
- **Остальные переменные дага** задаём через **Pydantic-класс конфига** в каталоге `dags_conf/`.
  - Имя класса = имя дага + суффикс `_conf` (например `aggregate_gamification_data_conf` для `dag_aggregate_gamification_data`).
  - Хранилище значений — Airflow Variable (JSON) **или** k8s Secret + ENV (как в эталонном приложении), согласно установке Airflow в проекте.
  - Инициализация конфига — в первых строках кода дага, **сразу после импортов**.
  - Новые значения вносятся в Variable/Secret в рамках MR ветки задачи.
- Если конфиг нового дага основан на Pydantic — добавить комментарии в исходник и ссылку в доку.

### §4.3 Top-level дага — чисто

- **Не использовать `Variable.get()` и тяжёлые импорты на top-level** DAG-файла.
- Все обращения к `Variable.get()` — внутри функций/операторов.
- На top-level — только импорты, нужные самому DAG'у. Тяжёлые библиотеки (`pandas`) и кастомные модули — **lazy-import внутри функций/операторов**. Top-level код выполняется при каждом парсинге дага шедулером — он должен быть лёгким.

### §4.4 Параметры оператора

- `KubernetesPodOperator` с `image`, `secrets=[Secret("env", ENV, "<k8s-secret>", key)]`, `env_vars=[V1EnvVar("RUN_ID", "{{ run_id }}")]`, `on_finish_action="delete_pod"`, `in_cluster=True`.
- `max_active_runs=1`, `catchup=False`, явный `execution_timeout`.
- `schedule`: `None` если триггерится извне; cron-строка если по интервалу. Sub-минутные интервалы кроном недостижимы — для частоты < 1 мин делать цикл внутри пода с паузой-настройкой.

### §4.5 Эволюция

- Существующие DAG'и **специально не переписываем**. Если правим — заодно подтягиваем схему работы с переменными/импортами к этому стандарту.

## §5. ClickHouse

- Клиент — `clickhouse_connect` (`clients/clickhouse.py`, `get_client(**client_params)`).
- **SQL только параметризованный** (`{name:Type}`), никаких f-строк со значениями (`security.md`, §11 python-standards). Идентификаторы (имена таблиц из доверенного конфига) допустимо подставлять f-строкой, значения — никогда.
- **Чтение больших выборок — стримом** (`query_row_block_stream` / итерация блоков). Не грузить миллионы строк в список — память пода ограничена, у сервера CH есть memory limit.
- **Вставка — батчами** (`client.insert(table, data, column_names)`), размер батча из настроек (`batch_size`, дефолт 100k). Накопил батч → flush → очистил.
- Идемпотентность чтения источника: либо file-checkpoint (по `object_key`), либо time-watermark (по времени окна). Курсор продвигаем **только после** успешной записи результата.
- **Время для CH — aware-UTC, не naive.** `clickhouse_connect` трактует **naive** `datetime` (в параметрах `{x:DateTime}` и в `client.insert`) как локальное время пода и конвертирует в UTC; колонки `DateTime` читаются/пишутся как naive UTC. На поде не в UTC это даёт сдвиг (напр. MSK → −3 ч) — оконные/watermark-фильтры по `uploaded_time` молча промахиваются мимо данных. Поэтому: `datetime.now(timezone.utc)`, при чтении из CH приводить naive→aware (`dt.replace(tzinfo=timezone.utc)`), в параметры/insert отдавать aware-UTC (или строки `'YYYY-MM-DD HH:MM:SS'`). Касается любой range/окно-логики.
- Партиционирование/skip-index: оконные запросы по неключевому полю (`uploaded_time`) требуют skip-index, иначе скан всей партиции. Индекс — предусловие запуска (pre-flight), не код приложения.
- DDL и очистка партиций — отдельными шагами/скриптами, не из приложения «на лету».

***

## §6. S3 / OBS

- Клиент — `boto3` (`clients/s3.py`). `addressing_style` — **в настройку, не хардкод**: для OBS обязательно `virtual` (без него обращения к бакету не работают), для локального MinIO на localhost — `path` (`virtual` там не резолвится, ломает локальную эмуляцию из §10). Таймауты/число ретраев boto3 (`read_timeout`, `connect_timeout`, `max_attempts`) — тоже из настроек.
- Большие выгрузки — резать на части по N записей/байт (настройка), заливать из tempfile стримом (`put_object` с file-like body), не держать всё в RAM.
- Ретраи с экспоненциальным backoff (настройки `max_retries`, `retry_backoff`).
- Ключи S3 — по согласованной convention (источник/дата/run_id/часть). Бакет — из настроек, должен быть из числа тех, что читает потребитель.

***

## §7. Kafka

- Воркер тоже тестируется локально перед MR (см. §10).
- Топики именуются: **источник → контур → сущность** (принятое в команде соглашение). После создания топик заносится в каталог топиков (реестр).
- Сообщения валидируются на границе (Pydantic), битые — в DLQ, не молча отбрасываются.

***

## §8. Нейминг данных (БД, таблицы, топики)

Принятое в команде соглашение об именовании (нет в общих стандартах):

- **Имя БД = имя источника**, откуда данные поступают изначально (например `crm` = данные из CRM).
- Суффиксы окружения в имени БД, где это принято (`crm_prod`, `crm_stage`).
- **Kafka-топик: источник → контур → сущность.**
- Любая новая таблица/вьюха/топик — **заносится в реестр** (каталог таблиц / каталог топиков), чтобы слой данных был задокументирован.

***

## §9. Состояние и идемпотентность

- Состояние пайплайна (что уже обработано) хранится явно: checkpoint-таблица (по файлам) или watermark-таблица (по времени).
- **Порядок коммита:** данные записаны в приёмник (CH/S3) → **затем** двигаем курсор → затем необязательные побочные действия (нотификация потребителя).
- Побочные действия (нотификация внешнего сервиса) — **best-effort**: оборачиваем, при недоступности логируем `error` и продолжаем, курсор не откатываем. Падение побочного шага не приводит к повторной обработке окна.
- Для восстановимости — флаг успеха побочного шага писать в лог-таблицу (например `notified UInt8`), чтобы пропущенные можно было повторить запросом.

## §10. Тестирование — локально и с эмуляцией (ОБЯЗАТЕЛЬНО)

Главное правило командного DoD: **«перед созданием MR работоспособность проверяем локально, прогоняем тесты».** Для дата-инженерных компонентов это значит — агент/разработчик обязан **сам поднять локальную эмуляцию и реально прогнать пайплайн**, а не ограничиться unit-тестами.

### §10.1 Локальная эмуляция (поднять и прогнать)

- Поднять зависимости локально через `docker-compose`: **ClickHouse**, **MinIO** (S3-совместимый, креды `minioadmin`/`minioadmin`), **Kafka** и **Postgres** — те, что нужны компоненту. Для DAG-компонентов — ещё и **локальный Airflow** (`airflow standalone` или docker-compose), чтобы реально спарсить и прогнать сам DAG, а не только зависимости.
- Две частые засады локального CH: (1) новые образы `clickhouse-server` **глушат сетевой доступ** для `default` без пароля — задать `CLICKHOUSE_USER`/`CLICKHOUSE_PASSWORD` в compose (пароль локальный, не секрет); (2) `clickhouse_connect` ходит по **HTTP-порту** (обычно `8123`), а не по нативному `9000` — в локальном `.env` указывать HTTP-порт. Для MinIO на localhost — `addressing_style=path` (см. §6).
- Прогнать приложение в режиме `--ingest`/`--export`/`--source` против локальных сервисов на маленьком объёме.
- Использовать тест-лимиты из настроек: `TEST_INGEST=true`, `TEST_INGEST_LIMIT`, `TEST_INGEST_ROW_LIMIT` (как в эталонном приложении), либо `dry_run`.
- Убедиться, что данные реально появились в локальном приёмнике (строки в CH / объекты в MinIO) и курсор/чекпойнт сдвинулся.
- **Локальное нагрузочное тестирование** (пункт DoD): на объёме проверить, что **нет утечки памяти** и скорость в ожидаемых рамках. Для стримовых выгрузок — что не грузим всё в RAM.

### §10.2 DAG локально

- Проверить, что DAG **парсится** (`python <dag_file>.py` без ошибок, либо `airflow dags list`/локальный standalone).
- Если локальный Python не тянет Airflow (слишком новая версия / нет нужной) — парсить через Docker-образ: `docker run --rm -v "$PWD":/opt/airflow/repo -e AIRFLOW__CORE__DAGS_FOLDER=/opt/airflow/repo/dags apache/airflow:<v> bash -c "airflow db migrate >/dev/null 2>&1 && airflow dags list-import-errors && airflow dags list"`. `list-import-errors` должно быть пусто. Реальный прогон KPO-таски требует k8s — бизнес-логику проверяем прогоном CLI против локальных CH/MinIO (это тот же код, что в поде).
- Проверить, что на top-level нет `Variable.get()` и тяжёлых импортов (§4.3).
- Прогнать таску дага локально против локальной эмуляции.

### §10.3 Unit-тесты (по testing.md + командному DoD)

- `pytest`, `from __future__ import annotations`, без `unittest.TestCase`.
- **Тест на каждый новый метод.** Структура зеркалит код: тест в папке `test_<dir>/`, файл `test_<name>.py`, для метода в классе — класс `Test<Name>` с `test_<method>`.
- Fake-клиенты вместо mock: `FakeClickHouse` (отдаёт заданные блоки), `FakeS3` (пишет в память), `FakeKafka`, `FakeNotifier` (умеет кидать исключение). Не `MagicMock`.
- Покрыть: happy path; пустое окно/файл; частичный объём; недоступность побочного шага (не падаем, курсор как ожидается); параметризацию SQL.

### §10.4 Definition of Done (data-eng)

Без этого таску не закрываем (свод командного DoD):

- [ ] Локально поднята эмуляция, пайплайн реально прогнан, результат проверен.
- [ ] Локальное нагрузочное: нет утечки памяти, скорость ок.
- [ ] Для ETL: **локальный прогон дага через Airflow обязателен** — не только парсинг, а зелёный `airflow dags test <dag_id> <date>` (при несовместимом локальном Python Airflow поднимать в Docker-образе `apache/airflow:<v>`, см. §10.2 — версия Python не повод пропустить шаг); новые переменные заведены в нужный Airflow; даг описан в доке; Pydantic-конфиг откомментирован + ссылка в доку.
- [ ] Для Kafka-воркера: воркер проверен локально; есть тесты; есть дока на воркер.
- [ ] Для БД-таски: проверено локально; тесты; при необходимости — индексы и очистка старых партиций в CH.
- [ ] Для «Kafka → CH»: поля добавлены в DDL-скрипт; при необходимости — очистка партиций.
- [ ] Линтер репо зелёный (тулчейн по §11), тесты зелёные.
- [ ] Дока обновлена; новая таблица/топик внесены в реестр.

## §11. Линтер и формат

- **Тулчейн — по факту целевого репо, не навязываем.** В легаси ETL-репозиториях pre-commit обычно настроен на `pycln` + `isort` + `black` + `flake8` + `mypy` + `bandit` (см. их `.pre-commit-config.yaml`). В FastAPI-сервисах (`python-standards.md`) — `ruff` + `basedpyright` через `uv`. Используем то, что стоит в репо, куда коммитим.
- Ruff в проектах с легаси внедряется итерационно: не блокируем работу, заводим таски на накопленные замечания.
- Pre-commit hook **или** линтер в IDE (Black/Ruff на сохранение) — по соглашению проекта; где-то pre-commit, где-то линтеры в IDE без хука. Главное — код проходит линтер репо до MR.

## §12. Документация и ревью

- На каждый компонент/даг/воркер — дока: что делает, как делает, основные настройки, рабочие URL. Чтобы понимать работу без чтения кода (`docs.md` + командное правило по докам). Схемы — `draw.io`/Mermaid, любая схема лучше отсутствия, но без перфекционизма.
- Кросс код-ревью: после MR и зелёных тестов пингуем ревьюверов своей группы (для дата-инженеров/ETL — своя группа), ревью в разумный SLA, апрув по кворуму.
- Коммиты: префикс — ID задачи; не включать в коммит папки сабмодулей.
