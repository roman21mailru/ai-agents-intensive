# Agent: Docs

## Когда обновлять документацию

- **Публичная функция / класс / метод добавлен или изменён** → обновить / написать docstring.
- **Эндпоинт, ENV-переменная, зависимость или команда запуска добавлены / изменены** → обновить README.md.
- **Принято решение, затрагивающее несколько модулей или меняющее публичный контракт** → создать ADR в `docs/adr/` (см. ниже: ADR-lite vs ADR-full).
- **Любое пользовательское изменение (новый эндпоинт, breaking change, фикс бага, новая конфигурация)** → добавить запись в `CHANGELOG.md` под `[Unreleased]`.

## Docstrings

- Формат — Google-style. Секции: одна строка-резюме, потом (при необходимости) `Args:`, `Returns:`, `Raises:`.
- **Docstring — на русском.** Имена параметров остаются английскими (это код), описание — на русском.
- Приватные функции (с `_` в начале) документировать по желанию, если они тривиальны.
- Запрещено: docstring повторяющий имя функции (`def get_user(): """Get user."""`). Либо объясняй зачем функция нужна, либо не пиши вообще.
- Примеры использования в docstring — только когда поведение неочевидно.

## CHANGELOG.md

- Стандарт — [Keep a Changelog](https://keepachangelog.com/).
- Секции `[Unreleased]`: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.
- Одна запись = одно пользовательское изменение, не один коммит. Рефакторинг без изменения поведения в CHANGELOG **не попадает**.
- Ссылки на Jira-тикет в скобках в конце записи: `- Added PATCH /links/{id} to update target_url (PROJ-101)`.

## ADR

ADR (Architecture Decision Record) — фиксация значимого технического решения.
Два формата по сложности: **ADR-lite** (быстрая фиксация) и **ADR-full**
(полный options analysis с матрицей оценки). Выбирай по триггерам ниже.

### Когда нужен ADR-full

Хотя бы один из триггеров срабатывает:

- Решение **дорого откатить** — миграция данных, смена БД / фреймворка / языка / схемы аутентификации.
- Решение **затрагивает > 1 репозитория** (в нашем случае — между `service-a-scraper`, `service-a-api`, `harvest_api`).
- Решение **влияет на NFR** — p99 latency, стоимость инфраструктуры, security / compliance.
- Решение **противоречит ранее принятому ADR** — тогда новый ADR помечает старый как `Superseded by NNNN`.
- В команде **идёт спор** с минимум двумя людьми с разными предпочтениями.
- Опций для выбора **≥ 3**.

### Когда достаточно ADR-lite

- Развилка с 2 опциями, обе несильно различаются.
- Решение внутри одного репозитория, откатывается одним коммитом.
- Не влияет на public API / БД / NFR.

Примеры ADR-lite: «логи через `structlog` с `ConsoleRenderer` в dev и `JSONRenderer` в prod», «именование роутов в множественном числе», «миграции — autogenerate + ручная проверка».

Примеры ADR-full: «хранилище статусов scraping-задач: PostgreSQL JSONB vs Redis vs in-memory + dump», «параллелизм воркеров: `asyncio.Semaphore` vs `multiprocessing` vs Celery», «JWT vs session-based auth».

### Путь и общие правила

- Путь: `docs/adr/NNNN-short-name.md`, где `NNNN` — следующий свободный номер.
- Не удалять ADR. Устаревшие помечаются `Superseded by NNNN`, но в репозитории остаются — это история решений.
- Каждый ADR (любого формата) добавляется в `docs/adr/INDEX.md` строкой: `NNNN | short-name | Status | дата | автор | теги`.

### Шаблон ADR-lite

```markdown
# NNNN — <короткое название решения>

## Status

Accepted

## Context

<Какая проблема? Какие были ограничения, требования, силы давления на решение?>

## Decision

<Что конкретно решили. Одно-два чётких предложения.>

## Consequences

<Что станет лучше? Что станет хуже? Какие риски остались принятыми?>

## Alternatives considered

- <Альтернатива 1>: почему не выбрали.
- <Альтернатива 2>: почему не выбрали.
```

### Шаблон ADR-full

```markdown
# NNNN — <короткое название решения>

## Status

Proposed | Accepted | Superseded by NNNN | Deprecated

## Y-формулировка

В контексте `<сценария>`, сталкиваясь с `<драйвером>`, мы решили
`<опция>` вместо `<альтернатив>`, чтобы достичь `<качества>`, принимая
`<компромисс>`.

> Пример: «В контексте scraping-воркера, сталкиваясь с требованием
> обрабатывать ≥ 200 задач/мин при p99 < 5с, мы решили использовать
> `asyncio.Semaphore(50)` вместо `multiprocessing.Pool(8)`, чтобы держать
> всё в одном async-процессе и переиспользовать httpx connection pool,
> принимая риск head-of-line blocking при тяжёлых CPU-операциях в
> обработчиках».

## Context

<2–5 абзацев: что заставило принимать это решение, какие факты на руках,
какие ограничения. Цифры, метрики, ссылки на Jira / эксперименты.>

## Decision drivers

Каждый драйвер **измеримый** или с явным критерием «как поймём, что
выполнен». Не «нужна производительность», а «p99 < 200мс при 100 RPS».
Не «нужна простота», а «новый разработчик в команде разбирается за 1 час
чтения кода».

1. <Драйвер 1, измеримый>
2. <Драйвер 2, измеримый>
3. <...>

## Considered options

- **Option A** — `<название>`. <1–2 предложения, что это.>
- **Option B** — `<название>`. <...>
- **Option C** — `<название>`. <...>

## Decision

Выбрана **Option `<буква>`**.

### Y-rationale

<1 абзац: почему именно эта опция оптимальна по совокупности драйверов.>

## Pros and cons of options

### Option A — <название>
- ✅ <плюс по конкретному драйверу>
- ✅ <плюс>
- ❌ <минус по конкретному драйверу>
- ❌ <минус>

### Option B — <название>
- ✅ <...>
- ❌ <...>

### Option C — <название>
- ✅ <...>
- ❌ <...>

## Evaluation matrix

> **Веса критериев зафиксированы `<ГГГГ-ММ-ДД>` ДО оценки опций.**
> Это правило-страховка от подгонки под ответ. Если после расчёта
> хочется поменять веса — это сигнал, что нужны дополнительные данные
> или PoC, а не редактирование весов.

| Критерий | Вес | Option A | Option B | Option C |
|---|---|---|---|---|
| <Драйвер 1> | 0.3 | 5 | 3 | 4 |
| <Драйвер 2> | 0.25 | 4 | 5 | 2 |
| <Драйвер 3> | 0.25 | 3 | 4 | 5 |
| <Operational simplicity> | 0.1 | 4 | 5 | 3 |
| <Cost> | 0.1 | 5 | 3 | 4 |
| **Итого (взвешенно)** | | **4.05** | 3.95 | 3.55 |

Шкала оценок: 1 = плохо, 5 = отлично. Не округляй до целого «потому что
лень» — 4.05 и 3.95 — это значимая разница, она указывает что выбор
неочевиден и нужна Sensitivity check.

## Sensitivity check

> **Обязательная секция. Без неё ADR остаётся в статусе `Proposed`.**

Вопрос: если поменять веса критериев на ±20%, изменится ли победитель?

- Если **нет** → решение устойчивое, переходим в `Accepted`.
- Если **да** → опции слишком близки, реального обоснования для выбора
  пока нет. Не утверждай ADR. Делай минимальный PoC (≤ 1 день) на
  спорных опциях, возвращай данные сюда, пересчитывай матрицу.

Конкретно для этого решения:
<«Перепроверил с весами драйвера 1 в диапазоне 0.2–0.4 — победитель не
меняется, Option A остаётся первой» / «PoC сделан, см.
`Tasks/<key>/poc-results.md`, цифры подставлены в матрицу выше».>

## Consequences

- ✅ <что станет лучше — конкретно, не «улучшится поддерживаемость»>
- ⚠️ <что станет сложнее, какие риски остаются принятыми>
- 🔄 <что нужно сделать в коде / инфраструктуре для реализации решения>

## Validation

Как поймём, что решение работает (через 1–3 месяца после реализации):
- <Метрика 1, ожидаемое значение>
- <Метрика 2, ожидаемое значение>
- <Какое событие триггерит пересмотр ADR>

## Links

- Jira: `<JIRA-KEY>`
- Артефакты задачи: `Tasks/<JIRA-KEY>/` (если есть архитектурный документ — `<JIRA-KEY>-architecture.md`)
- Связанные ADR: NNNN (...), MMMM (...)
- Внешние источники: <ссылки на статьи / документацию, если опирались>
```

### Правила для ADR-full

- **Веса критериев фиксируются ДО оценки опций.** Это главная защита от
  confirmation bias. Запиши веса, потом проставь оценки. Не наоборот.
- **Sensitivity check обязателен.** Пустая секция = ADR не принят, статус
  `Proposed`. Это правило железное.
- **Драйверы должны быть измеримыми.** «Нужна производительность» — не
  драйвер. «p99 < 200мс на нагрузке X» — драйвер.
- **Не больше одного автора и одного ревьюера на ADR.** Если хочется
  больше — значит решение спорное, и нужно сначала достичь консенсуса
  голосом / в чате, а ADR только фиксирует результат.

## README.md

- Разделы (минимум): Overview, Quickstart, Configuration (ENV), Running (dev / tests / migrations), Architecture (короткая схема слоёв), API (ссылка на `/schema/swagger`).
- Обновляется в том же коммите, где меняется соответствующее поведение. Устаревший README — блокер мержа.

## Запрещено

- Коммит публичного API без docstring.
- Новый эндпоинт / breaking change без записи в CHANGELOG.
- Архитектурное решение без ADR (если есть сомнения — создать ADR-lite, его легче, чем спорить нужен или нет).
- Удаление ADR. Устаревшие ADR помечаются статусом `Superseded by NNNN`, но не удаляются — история решений сохраняется.
- Автогенерация docstring-ов в стиле «Does the thing» — лучше без docstring, чем с мусорным.
- ADR-full с **пустой** Sensitivity check (статус остаётся `Proposed`, ADR не считается принятым).
