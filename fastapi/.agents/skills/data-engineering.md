# Skill: Data Engineering

## Алгоритм выполнения дата-инженерной задачи

> Применять для ETL-приложений, Airflow DAG'ов, Kafka-воркеров, загрузки в
> ClickHouse и выгрузки из CH в S3. Правила (декларативные) — в
> `.agents/agents/data-engineering.md`. Этот skill — пошаговый алгоритм.
> Эталон кода — референсный ingest-модуль команды.

### 1. Подготовка
- Уточнить, что за компонент: ETL-app / DAG / Kafka-воркер / CH-загрузка / CH→S3.
- Найти Jira-задачу, создать ветку от dev: имя = ID задачи.
- Прочитать `.agents/agents/data-engineering.md` и, если задача большая (≥ 1 дня),
  оформить architecture-документ по `.agents/skills/architecture.md`.
- Найти эталон рядом (референсный ingest-модуль) и копировать его структуру, не изобретать.

### 2. Изучение
- Понять источник и приёмник данных, их формат и объём.
- Определить состояние: file-checkpoint (по объектам) или time-watermark (по времени).
- Проверить нейминг (БД = источник; топик = источник→контур→сущность) и реестр
  таблиц/топиков — не плодить дубли.
- Свериться с тулчейном репо (`.pre-commit-config.yaml`): какие линтеры реально стоят.

### 3. Реализация (структура как у эталона)
1. `settings.py` — `pydantic-settings`, вложенные модели на источник,
   `env_nested_delimiter="__"`, пустая строка → `None` (`BeforeValidator`),
   секреты из ENV, целевые имена таблиц/бакетов/топиков — в настройки, не в код.
2. `cli.py` / `app.py` — argparse + dispatch по режимам, без бизнес-логики.
3. `clients/` — тонкие фабрики: `clickhouse_connect`, `boto3` (virtual addressing),
   `psycopg`. Синхронные (это batch, не async-сервис — см. §1.1 стандарта).
4. Бизнес-логика в `ingest/`/`export/`: CH-чтение **стримом**, вставка **батчами**,
   SQL только **параметризованный**, S3 — резка на части + стрим из tempfile.
5. `storage/` — checkpoint/watermark и лог батчей. Курсор двигаем **после** записи
   данных; побочные шаги (нотификация) — best-effort (поймать, залогировать `error`,
   не откатывать курсор).
6. Magic numbers → `const.py`. Все функции с аннотациями и docstring на русском.

### 4. DAG (если есть)
- Имя файла DAG = ID дага; слово «DAG» в имени не писать.
- Конфиг дага — Pydantic-класс `<dag_id>_conf` (в `dags_conf/` или как
  `pydantic-settings` из ENV, по установке Airflow в репо); инициализация в первых
  строках после импортов; значения в Airflow Variable (JSON) или k8s Secret.
- **Top-level дага чистый:** нет `Variable.get()` и тяжёлых импортов (`pandas`,
  кастомные модули) на верхнем уровне — только lazy-import внутри функций/операторов.
- `KubernetesPodOperator`: `max_active_runs=1`, `catchup=False`, `execution_timeout`,
  `is_delete_operator_pod=True`, секреты через `Secret("env", ...)`.
- Существующие DAG'и без нужды не переписывать.

### 5. Тестирование — ЛОКАЛЬНО С ЭМУЛЯЦИЕЙ (обязательно)
Это главный шаг. Агент **сам** поднимает эмуляцию и реально прогоняет пайплайн,
а не ограничивается unit-тестами.

1. Поднять `docker-compose` с нужными сервисами: **ClickHouse**, **MinIO**
   (`minioadmin`/`minioadmin`), **Kafka**, **Postgres** — что нужно компоненту.
2. Прогнать приложение против локальных сервисов на малом объёме
   (`TEST_INGEST=true`, `TEST_INGEST_LIMIT`, `TEST_INGEST_ROW_LIMIT` или `dry_run`).
3. Проверить результат: строки появились в локальном CH / объекты в MinIO,
   курсор/чекпойнт сдвинулся как ожидается.
   Для каждого типа объекта проверить через `head_object`, а не только по имени: key имеет
   осмысленное расширение, `ContentType` соответствует реальным bytes, bucket/prefix детерминирован.
   Изображения/PDF/media должны быть пригодны для встроенного preview Console; JSON хранится как
   `.json`/`application/json`, даже если конкретная Console не имеет inline JSON viewer.
   Публичный URL Console и bucket задаются конфигурацией, не хардкодятся. Не обещать plugin viewer:
   сначала доказать наличие поддерживаемого extension API у используемой версии Console.
4. **Локальное нагрузочное:** на объёме убедиться, что нет утечки памяти и скорость
   в ожидаемых рамках (для стрим-выгрузок — что не грузим всё в RAM).
5. DAG: проверить, что парсится (`python <dag>.py` без ошибок), top-level чистый,
   таска прогоняется локально.
6. Unit-тесты (`pytest`, Fake-клиенты `FakeClickHouse`/`FakeS3`/`FakeKafka`, не mock):
   тест на каждый новый метод, структура `test_<dir>/test_<name>.py`, `Test<Class>`.

### 6. Финальная проверка (тулчейн репо)
- Прогнать линтеры/форматтеры, которые стоят в репо. Например, для легаси ETL-репо:
  `pre-commit run --all-files` (pycln, isort, black, flake8, mypy, bandit).
  Для Litestar-репо — `uv run ruff check . && uv run basedpyright && uv run pytest -q`.
- Все тесты зелёные, включая прогон против локальной эмуляции.
- При нетривиальном падении — `.agents/agents/error-handling.md`
  (Identify → Assess → Communicate → Solutions), не лепить workaround.

### 7. Документация и DoD
Пройти DoD из `.agents/agents/data-engineering.md` §10.4:
- ETL: даг проверен локально, переменные заведены в Airflow, даг описан в доке,
  Pydantic-конфиг откомментирован + ссылка в доку.
- Kafka-воркер: проверен локально, тесты, дока на воркер.
- БД-таска: проверено локально, тесты, при необходимости индексы + очистка партиций CH.
- «Kafka → CH»: поля добавлены в DDL-скрипт, при необходимости очистка партиций.
- Новая таблица/топик внесены в реестр. Дока обновлена.

### 8. Коммит и ревью
- Коммит: префикс — ID задачи; не включать папки сабмодулей.
  Формат и язык — по `.agents/AGENTS.md` (тэг английский, описание русское).
- Кросс код-ревью: после зелёных тестов пингуем ревьюверов своей группы (для
  дата-инженеров — своя группа), апрув по кворуму.
