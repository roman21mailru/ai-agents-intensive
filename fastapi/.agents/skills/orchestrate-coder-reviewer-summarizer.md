# Coder → Reviewer → Summarizer

Оркестрировать три специализированные роли как конечный автомат. Не просить один контекст
«сыграть троих»: каждый worker должен стартовать отдельным вызовом или отдельным субагентом,
получать только свой вход и оставлять машинно-проверяемый handoff.

## Нерушимые правила

1. Держать единственного владельца состояния: Orchestrator. Только он выбирает следующую роль,
   считает итерации, запускает гейты и решает, остановить ли цикл.
2. Разрешать менять продуктовый код только Coder. Reviewer и Summarizer держать read-only и
   дополнительно проверять отпечатком worktree до/после.
3. Не доверять самоотчёту роли. Проверять тесты, линтеры, схему handoff, evidence и отсутствие
   неожиданных правок детерминированными командами.
4. Не запускать Summarizer после `CHANGES_REQUESTED`, `BLOCKED`, красного гейта или невалидного
   handoff. Возвращать конкретные findings Coder.
5. Ограничивать цикл числом итераций и wall-clock бюджетом. После повторения того же блокера два
   раза останавливать автоматический луп и эскалировать человеку.
6. Не открывать PR, не пушить и не отправлять сообщения без явного разрешения. Summarizer готовит
   артефакты локально; внешнее действие остаётся отдельным шагом.
7. Не передавать секреты, полный чат или скрытые рассуждения. Передавать задачу, факты, diff,
   результаты команд, решения и открытые риски.

## Выбрать топологию

| Форма задачи | Топология |
|---|---|
| Один малорисковый файл, очевидная проверка | Один агент + обычный deterministic gate |
| Связный diff, нужен независимый review и PR-текст | Базовый последовательный pipeline этого скилла |
| Diff затрагивает несколько независимых осей качества | Coder → fan-out read-only reviewers → Synthesizer → Summarizer |
| Критичная архитектура, безопасность или деньги | Pipeline + внешний экспертный совет/человек как отдельный acceptance gate |
| Несколько независимых реализаций без общих файлов | Fan-out writers в отдельных worktree; не смешивать с базовым циклом |

Начинать с базового pipeline. Добавлять веер или совет только когда форма задачи оправдывает
стоимость и сложность. В этом учебном проекте используется только базовый
последовательный pipeline; расширения не материализуются.

## Preflight

1. Прочитать корневой `AGENTS.md` и все указанные им правила/скиллы репозитория.
2. Проверить `git status`; сохранить существующие изменения пользователя и не смешивать их с
   задачей. При грязном worktree зафиксировать baseline-отпечаток, но не делать reset/checkout.
3. Сформировать task envelope:
   - цель и границы;
   - acceptance criteria;
   - разрешённые и защищённые пути;
   - обязательные gate-команды;
   - `max_iterations` (обычно 2, максимум 3 без нового решения человека);
   - runner/model policy;
   - условия немедленной эскалации.
4. Использовать OpenCode-adapter из §15.2: отдельный `opencode run --format json`
   для каждой роли, без `--continue` и `--session`.
5. Создать отдельный каталог прогона, например `.ai-team/runs/<run-id>/`; не использовать общие
   `coder.json` между параллельными прогонами. Lock должен относиться к одному `run-id`.
6. Снять baseline тестов и качества до Coder. Красный baseline не приписывать новому diff;
   остановиться или явно записать известный долг в task envelope.

## Конечный автомат

```text
INIT → CODER → CODE_GATE → REVIEWER → REVIEW_GATE
                                  ├─ CHANGES_REQUESTED → CODER (iteration + 1)
                                  ├─ BLOCKED/invalid → ESCALATE
                                  └─ MERGE → SUMMARIZER → FINAL_GATE → READY_FOR_PR
```

Текстовый эквивалент: Coder реализует изменение; deterministic gate проверяет код; Reviewer
независимо принимает или возвращает diff; только принятый diff попадает Summarizer; финальный
гейт сверяет PR-артефакт с кодом и тестами.

## Шаг 1. Запустить Coder

Передать Coder только:

- task envelope и текущие acceptance criteria;
- правила проекта и релевантный feature/bugfix/refactoring skill;
- разрешённые пути;
- findings предыдущего Reviewer, если это fix-итерация;
- формат `coder` handoff.

Разрешить чтение, изменение файлов и безопасные команды внутри корня проекта. Запретить push,
merge, публикацию, изменение защищённых путей, ослабление тестов/гейтов и обход hooks.

Потребовать в финале JSON handoff с перечнем изменённых файлов, выполненных команд и кодов
выхода, допущений, рисков и незавершённого. Не считать `tests pass` доказательством.

Провалидировать handoff явными проверками обязательных полей из project-local
`.opencode/agents/coder.md`; не принимать пустые массивы changed_files и нечисловые exit code.

## Шаг 2. Выполнить CODE_GATE

Orchestrator, а не Coder, запускает:

1. проверку изменённых путей против allowlist/protected paths;
2. formatter check, lint, typecheck и тесты из task envelope;
3. targeted regression test минимум дважды, если изменение связано со временем,
   конкурентностью, случайностью или сетью;
4. `git diff --check` и поиск секретов, если это принято в проекте;
5. сохранение `diff.patch`, stdout/stderr и exit codes в каталог прогона.

Красный CODE_GATE не передавать Reviewer как готовый результат. Вернуть Coder конкретный лог,
если остался бюджет; системный блокер или повтор того же падения эскалировать.

## Шаг 3. Запустить Reviewer

Стартовать Reviewer со свежим контекстом. Передать только:

- task envelope и acceptance criteria;
- реальный diff/изменённые файлы;
- `coder.json` как заявление, которое нужно проверить, а не как источник истины;
- логи CODE_GATE;
- project review skill и формат `reviewer` handoff.

Reviewer обязан:

- работать read-only;
- проверить контракт, архитектурные границы, корректность, тесты, безопасность и регрессии;
- вынести два независимых под-вердикта: `spec_verdict` (сделано ли ровно требуемое) и
  `quality_verdict` (хорошо ли это реализовано);
- привязать каждую находку к файлу, строке и дословному evidence из первоисточника;
- выставить каждому finding строго `status=CONFIRMED` или `status=INCONCLUSIVE`: проверенный дефект —
  `CONFIRMED`, внешний факт без доказательства в worktree — `INCONCLUSIVE`;
- использовать `INCONCLUSIVE` для непроверенного внешнего факта;
- вернуть `MERGE`, `CHANGES_REQUESTED` или `BLOCKED`.

Перед Reviewer снять отпечаток:

```bash
mkdir -p .ai-team/fingerprints
python3 .agents/scripts/worktree_fingerprint.py --write .ai-team/fingerprints/reviewer.before
```

После Reviewer сравнить:

```bash
python3 .agents/scripts/worktree_fingerprint.py --compare .ai-team/fingerprints/reviewer.before
```

Любое изменение worktree Reviewer'ом считать нарушением роли, даже если код «стал лучше».

## Шаг 4. Разобрать вердикт

- `MERGE`: убедиться, что блокирующих findings нет; перейти к Summarizer.
- `CHANGES_REQUESTED`: передать Coder только подтверждённые findings, их evidence и
  acceptance criteria; увеличить iteration; после фикса повторить CODE_GATE и запустить новый
  Reviewer-context.
- `BLOCKED`: остановить цикл и описать недостающую власть/информацию/внешнее состояние.
- Невалидный JSON или пустой ответ: один format-retry без изменения задачи; второй провал
  перевести в `BLOCKED`.

Не позволять Coder закрывать finding словами. Reviewer следующей итерации проверяет diff и
фактический тест. Не позволять Reviewer вводить новые требования вне task envelope; такие идеи
писать как non-blocking follow-up.

## Шаг 5. Запустить Summarizer

Summarizer запускать только после `MERGE`. Держать его read-only и передать:

- task envelope;
- принятый diff и список файлов;
- `coder.json`, итоговый `reviewer.json` и deterministic gate logs;
- шаблон PR/MR проекта;
- формат `summarizer` handoff.

Summarizer формирует доказательный локальный артефакт:

- заголовок и краткое «зачем»;
- изменения по слоям;
- test plan с реально выполненными командами;
- риски, совместимость, rollback;
- связанные follow-ups;
- решение `READY_FOR_PR` или `BLOCKED`.

Не разрешать фразы вроде `added some changes`: каждый пункт должен подтверждаться diff или
gate log. Снять и сравнить отпечаток worktree так же, как для Reviewer, затем выполнить:

Проверить JSON Summarizer явным fail-closed гейтом: verdict `READY_FOR_PR`, непустой
`claim_ledger`, у каждого claim есть непустой текст и существующий `path:line`.

## Шаг 6. Выполнить FINAL_GATE

Перед статусом `READY_FOR_PR` проверить:

- итоговый Reviewer дал `MERGE`, а его handoff валиден;
- все deterministic gates зелёные после последней правки Coder;
- Summarizer не изменил код;
- каждый пункт PR description подтверждается diff/log;
- открытые риски не спрятаны;
- число итераций и стоимость записаны;
- внешние действия ещё не выполнены без разрешения.

Отдать пользователю код/локальные артефакты и короткий audit trail: роли, итерации, гейты,
вердикт, остаточные риски.

## Stop conditions

Немедленно остановить автоматический цикл при любом условии:

- достигнут `max_iterations`;
- один и тот же blocking finding повторился два review-раунда;
- Reviewer или Summarizer меняет продуктовый worktree;
- handoff невалиден после одного format-retry;
- Coder ослабил тест/гейт, изменил protected path или вышел за allowlist;
- baseline красный и невозможно отделить старый дефект от нового;
- спор требует продуктового/архитектурного решения человека;
- исчерпан token/wall-clock budget;
- отсутствует требуемая авторизация для внешнего действия.

При остановке сохранить состояние и следующий безопасный шаг. Не крутить цикл «ещё раз» без
новой информации.

## Расширения

- Веер Reviewer в этом учебном проекте не материализован: §15.2 использует одну
  последовательную read-only роль Reviewer.
- Для OpenCode использовать project-local `.opencode/agents/*.md` и deny-permissions;
  исполняемый adapter находится непосредственно в §15.2.
- Для OpenCode всегда отделять transport от handoff: `--format json` →
  `.agents/scripts/extract_opencode_text.py` → явный role validator из §15.2.
  Не парсить цветной default stdout.
- Пример FastAPI/TTL, stop conditions и диагностика полностью описаны в §15.2;
  скрытых обязательных reference-файлов у student edition нет.

## Definition of Done

- Три роли действительно разделены вызовами и правами.
- Reviewer и Summarizer механически read-only.
- Handoff каждого перехода валиден и минимален.
- Красный review возвращается Coder, зелёный ведёт к Summarizer.
- Цикл ограничен и возобновляем из артефактов.
- Финальный PR description подтверждается diff и командами.
- Публикация не происходит как скрытый побочный эффект.
