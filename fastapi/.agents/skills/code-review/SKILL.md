# Skill: Code Review

## Цель

Проверить что код соответствует стандартам из `.agents/agents/python-standards.md`
и архитектурным правилам из `.agents/agents/architecture.md`.

***

## Алгоритм

### 1. Запустить автоматические проверки

~~~bash
uv run ruff check <файл_или_папка>
uv run basedpyright <файл_или_папка>
~~~

Включить результаты в отчёт. Автоматические ошибки не пересказывать — только итог.

### 2. Прочитать файлы под ревью полностью

### 3. Проверить по чеклисту

#### 🔴 Блокирующие (merge запрещён до исправления)

- [ ] `from __future__ import annotations` — первая строка в файле
- [ ] Все параметры функций аннотированы
- [ ] Все функции имеют аннотацию возвращаемого типа (включая `-> None`)
- [ ] Нет `Optional[X]`, `List[X]`, `Dict[K,V]` — только `X | None`, `list[X]`, `dict[K,V]`
- [ ] Нет `-> dict` как публичного контракта — только DTO/Value Object
- [ ] Сервисный слой не импортирует `db/models.py` напрямую
- [ ] Бизнес-логика не в route handlers
- [ ] Нет `except Exception: pass`
- [ ] Нет мутируемых значений по умолчанию (`= []`, `= {}`)
- [ ] **Async-инварианты (§5):** проект полностью async — нет `from sqlalchemy.orm import Session` (только `AsyncSession`), все DB-методы `async def` + `await session.execute(...)`, сервис вызывает репозиторий через `await`, handler'ы `async def` + `await service.X(...)`. Sync-вызов в async-контексте блокирует event loop и валит производительность.
- [ ] **Никаких `next(generator_func())` для async-генераторов** — это просто не работает (нужен `anext()` или `async for`). Признак copy-paste из старого sync-кода.
- [ ] **Логирование (§13):** нет `print()`, нет f-строк в `logger.info(...)`, нет секретов / токенов / Authorization в kwargs.
- [ ] **Безопасность (§14):** нет хардкода секретов, SQL параметризован, пароли через `bcrypt`/`argon2`, HTTP-клиенты с `timeout=` и `verify=True`, `subprocess` без `shell=True` с user input.
- [ ] **Дефолт не выключает фичу.** Для каждого нового параметра спросить: если оставить дефолт, фича делает свою работу? Ноль, пустая строка или `None` у поля, которое управляет самой сутью фичи (ожидание рендера, глубина обхода, лимит выборки), — это выключатель, замаскированный под настройку. Такой параметр либо обязательный без дефолта, либо с рабочим дефолтом.
- [ ] **Есть тест на payload внешнего вызова, а не только на его код возврата.** Если фича обращается к внешнему сервису, должен быть тест, что в запрос ушло рабочее значение параметра. Ответ 200 ничего не доказывает, если мы попросили сервис ничего не делать.
- [ ] **Новый параметр окружения выставлен на всех стендах в этом же MR.** Параметр, которого нет ни в одном values, ревью не ловит: сравнивать не с чем, аномалия невидима.
- [ ] **Предъявлен бизнес-результат, а не только зелёный прогон.** Для фичи, меняющей содержимое или объём данных, автор обязан приложить срез до/после по метрике с текстом запроса и открыть вручную не менее 5 записей результата. «Тесты зелёные», «воркер работает», «файлы пишутся» — не доказательство. Нет среза — это блокирующее замечание, а не пожелание.

#### 🟡 Некритичные (рекомендации, исправить в следующем PR)

- [ ] Нет магических чисел — только именованные константы
- [ ] Нет дублирования логики (DRY)
- [ ] Функция делает одно дело (SRP), не длиннее 30-40 строк
- [ ] Именование: `snake_case` / `PascalCase` / `UPPER_SNAKE_CASE`
- [ ] Параллельные задачи через `asyncio.TaskGroup`, не `gather()` (когда не нужен `return_exceptions=True`) — §5
- [ ] Современный синтаксис: `type UserId = int` (PEP 695), `Self`, `match/case`, `StrEnum` где уместно — §15
- [ ] Coverage на новой логике не понижает общий процент ниже 80% (`--cov-fail-under=80`)

## Формат отчёта

~~~text
## Code Review: <файл или ветка>

### Автоматические проверки
ruff: X ошибок | basedpyright: Y ошибок

### Нарушения

#### 🔴 Блокирующие

| # | Файл | Строка | Нарушение | Стандарт |
|---|------|--------|-----------|----------|
| 1 | bad_link_service.py | 1 | Отсутствует `from __future__ import annotations` | python-standards §1 |

#### 🟡 Некритичные

| # | Файл | Строка | Нарушение | Стандарт |
|---|------|--------|-----------|----------|
| 1 | bad_link_service.py | 45 | Магическое число `75` | python-standards §8 |

### Бизнес-результат
Срез до/после: <метрика, запрос, значения> | Открыто вручную записей: N
Дефолты новых параметров: <какие проверены и что фича при них работает>

### Итог
- Блокирующих: X
- Рекомендаций: Y
- Вердикт: ❌ Требует правок / ✅ Можно принимать
~~~

> Секция «Бизнес-результат» обязательна и не заполняется словами. Если автор не предъявил
> срез, ревьюер пишет туда «не предъявлен» и ставит блокирующее замечание. Реальный кейс
> (GigaExplorator, 08.2026): параметр ожидания рендера прошёл ревью с `default=0`, потому
> что проверяли соответствие стандартам, а не то, что фича делает свою работу. Четыре дня
> прода, 27,6% пригодных страниц вместо ожидаемых.

## Комментарий в MR: чистый текст и минимальный объём

Формат отчёта выше — рабочая форма ревьюера, чтобы ничего не потерять. **То, что уходит
в комментарий MR, пишется сплошным текстом**, а объём режется до минимума, при котором
автор всё ещё может исправить замечание, не переспрашивая.

Чеклист приёмки комментария — проверяется до отправки, каждый пункт:

- [ ] **Сплошной текст.** Ни таблиц, ни заголовков, ни эмодзи-маркеров, ни вложенных
      списков. Абзац на смысловой блок.
- [ ] **Абзацы объединены до предела.** Два соседних абзаца об одном замечании — это
      один абзац. Если абзац можно вклеить в предыдущий без потери смысла, вклеить.
- [ ] **Нет пересказа формата.** «Автоматические проверки», «Итог», «Вердикт» как
      отдельные секции не выносятся: результат прогонов — одна строка, вердикт — одна
      фраза в конце.
- [ ] **Нет повторов.** Замечание формулируется один раз. Не дублировать его в сводке,
      в таблице и в тексте — выбрать текст.
- [ ] **Каждое замечание = что не так + чем доказано + что сделать.** Без этих трёх
      частей строка не нужна; с ними — лишние слова вокруг не нужны тем более.
- [ ] **Пути и символы вместо описаний.** `state_manager.py:40-42` короче и точнее, чем
      абзац про то, где читается модель.
- [ ] **Закрытые пункты — одной строкой скопом**, а не по абзацу на каждый: автор уже
      знает, что он чинил, ему важно только подтверждение.
- [ ] **Убрано всё, что не меняет действий автора**: похвала, рассуждения о том, что
      риска нет, пересказ того, как работает его же код.

Правило простое: сначала пишется полный отчёт по форме выше — для себя, чтобы проверить
полноту. Потом он сжимается в комментарий и **из комментария удаляется всё, после
удаления чего автор всё ещё знает, что чинить**. Длинное ревью не читают целиком, и
блокирующее замечание тонет среди аккуратности.
